# ЕДОНДОН — Архитектура MVP (Шаг 2)

> Статус: **в работе**. Проектирование под решения Шага 1.
> Стек зафиксирован владельцем: **TypeScript + Cloudflare Workers** (free tier хватает до ~1000 польз./день).
> ИИ: **Cloudflare Workers AI** (vision-модель в той же экосистеме, без внешней оплаты). КБЖУ — только от модели (Open Food Facts — позже). Код MVP пишет Claude.

---

## 1. Принципы и ограничения платформы
Cloudflare Workers — serverless edge-рантайм. Из этого следует:
- **Только webhook** для Telegram (long polling невозможен — нет постоянного процесса).
- **Без локального диска и постоянной памяти** между запросами → состояние только во внешних хранилищах CF.
- **Лимиты free tier:** ~100 000 запросов/день, CPU ~10 мс/запрос (бесплатно), до 50 мс на платном. Долгие LLM-вызовы идут как `fetch` (сетевое ожидание не ест CPU-бюджет, но есть общий лимит времени) → тяжёлую работу выносим в `waitUntil`/очередь.
- **Секреты** (`BOT_TOKEN`, `LLM_API_KEY`) — через `wrangler secret`, не в коде.

## 2. Компоненты Cloudflare
| Компонент | Назначение |
|---|---|
| **Workers** | Точка входа: приём Telegram webhook, маршрутизация, бизнес-логика. |
| **D1** (SQLite) | Реляционные данные: пользователи, дневник питания, замеры состояния, цели, события аналитики. |
| **KV** | Состояние диалога (FSM-сессии), кэш справочника продуктов/КБЖУ, троттлинг. |
| **R2** | Хранение фото еды (опционально — для дообучения/аудита; в MVP можно не хранить, см. §7). |
| **Workers AI** | Распознавание фото (vision) и генерация советов — биндинг `env.AI`, без внешнего API-ключа. |
| **Queues** *(опц.)* | Асинхронная обработка фото→AI, чтобы webhook отвечал Telegram мгновенно (200 OK). |
| **Secrets** | `BOT_TOKEN` (Workers AI — через биндинг, отдельный ключ не нужен). |

## 3. Библиотеки
- **grammY** — Telegram-фреймворк, первоклассно работает на Workers (`webhookCallback`), есть сессии и FSM-плагины.
- **Zod** — валидация ответов модели (строгий JSON-контракт КБЖУ).
- **Drizzle ORM** *(опц.)* — типобезопасный доступ к D1.
- **Workers AI** — через биндинг `env.AI.run(model, ...)`. Кандидаты vision-моделей: `@cf/meta/llama-3.2-11b-vision-instruct`, `@cf/llava-hf/llava-1.5-7b-hf`. Текстовые советы — Llama 3.x instruct.
- **Тонкая абстракция `AIProvider`** — единый интерфейс `recognizeFood(image)` / `advise(context)`. Реализация по умолчанию — Workers AI; при слабом качестве vision можно подменить на внешний провайдер без правки бизнес-логики.

## 4. Поток данных (happy path)
```
Telegram → webhook → Worker
  1. Пользователь шлёт фото еды
  2. Worker отвечает 200 OK сразу + ставит задачу (Queue/waitUntil): "анализ фото"
  3. Воркер берёт file_id → Telegram getFile → скачивает байты → base64
  4. Вызов Workers AI (vision): {изображение} → JSON {блюдо, КБЖУ, порция, уверенность}
  5. Валидация Zod; бот шлёт карточку "Это [блюдо], ~X ккал. Верно?" + кнопки правки
  6. После подтверждения → запись в D1 (food_log)
  7. Чек-ин состояния (энергия/голод/стресс) — инлайн-кнопки → state_log
  8. По запросу/триггеру: AI-совет на обед/ужин (контекст: дневник дня + цели + состояние)
  9. Формирование корзины по дефицитам → сообщение со ссылкой/диплинком
 10. Каждое ключевое действие → analytics_events
```

## 5. Модель данных (D1, черновик схемы)
```sql
users (
  id INTEGER PRIMARY KEY,          -- внутренний
  tg_id INTEGER UNIQUE,            -- Telegram user id
  created_at TEXT,
  goal_kcal INTEGER, goal_prot INTEGER, goal_fat INTEGER, goal_carb INTEGER,
  tz TEXT                          -- таймзона для «дня»
);

food_log (
  id INTEGER PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),
  ts TEXT,                         -- время приёма
  dish_name TEXT,
  kcal REAL, prot REAL, fat REAL, carb REAL,
  portion_g REAL,
  confidence REAL,                 -- уверенность распознавания
  source TEXT,                     -- 'llm' | 'manual_edit'
  photo_key TEXT                   -- ключ в R2 (nullable)
);

state_log (                        -- замер самочувствия
  id INTEGER PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),
  ts TEXT,
  energy INTEGER,                  -- шкала 1..5
  sleepiness INTEGER,
  hunger_spike INTEGER,
  irritability INTEGER,
  stress INTEGER,
  note TEXT                        -- nullable, свободный комментарий
);

recommendations (
  id INTEGER PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),
  ts TEXT, meal TEXT,              -- 'lunch'|'dinner'
  text TEXT, basket_json TEXT      -- сформированная корзина
);

analytics_events (
  id INTEGER PRIMARY KEY,
  user_id INTEGER, ts TEXT,
  event TEXT,                      -- 'photo','confirm','edit','state_checkin','rec_shown','basket_click'
  payload_json TEXT
);
```

## 6. Контракт модели (строгий JSON)
Распознавание (vision, Workers AI) возвращает **только JSON**, валидируется Zod:
```json
{
  "dish": "string",
  "portion_grams": 0,
  "kcal": 0, "protein": 0, "fat": 0, "carb": 0,
  "confidence": 0.0,
  "assumptions": "string"
}
```
- **Митигация веса порции** (ключевой риск из анализа): если `confidence` низкая или порция неоднозначна — бот задаёт уточняющий вопрос («сколько примерно граммов / размер порции?») перед записью.
- Совет нутрициолога — отдельный промпт: вход = агрегаты дня (КБЖУ, остаток до цели) + последние замеры состояния; выход = текст + список продуктов корзины (JSON).
- **Дисклеймер** «не медицинский совет» — в онбординге и под советами (регуляторный риск).

## 7. Приватность фото
- В MVP по умолчанию **фото не храним** в R2: скачали → отправили в LLM → выбросили; в D1 только результат.
- Опция хранения в R2 — за явным согласием (для будущего дообучения/аудита). Решение можно отложить.

## 8. Окружения и деплой
- `wrangler.toml`: биндинги D1/KV/R2, маршруты, переменные.
- Окружения: `dev` (тестовый бот) и `prod`.
- Деплой: `wrangler deploy`; webhook ставится через `setWebhook` на URL воркера.
- Миграции D1 — через `wrangler d1 migrations`.

## 9. Аналитика и KPI (из Шага 1)
Таблица `analytics_events` покрывает KPI-набор:
- **Удержание/частота:** события `photo`, активные дни (по `users`+`food_log`).
- **Точность/доверие:** доля `edit` к `confirm`, средняя `confidence`.
- **Интерес к корзине:** `basket_click` / `rec_shown` (CTR).

## 10. Решения и открытые вопросы
**Зафиксировано:**
- ✅ ИИ — **Cloudflare Workers AI** (биндинг `env.AI`, без внешней оплаты), за тонкой абстракцией `AIProvider`.
- ✅ КБЖУ — **только от модели** в MVP (помечено как оценочное); Open Food Facts — в бэклог.

**Решу сам по ходу реализации (не блокирует):**
- [ ] Cloudflare Queues vs `waitUntil` — выберу по реальному времени ответа vision-модели.
- [ ] Drizzle ORM или «голый» D1 SQL — склоняюсь к Drizzle ради типобезопасности.
- [ ] Конкретная vision-модель Workers AI (llama-3.2-vision vs llava) — по качеству на тестовых фото.
