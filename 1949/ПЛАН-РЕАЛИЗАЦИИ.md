# ЕДОНДОН — План реализации MVP (Шаг 3)

> Стек: TypeScript + Cloudflare Workers + Workers AI + D1/KV/R2. UI: гибрид (бот + Telegram Mini App).
> Код пишет Claude инкрементально; каждый этап — отдельный проверяемый кусок.
> Учтены пробелы из `ПРОТОТИП-РАЗБОР.md` и аддендум §16 требований.

## Подход
Идём вертикальными срезами: сначала «скелет, который запускается и отвечает», потом наращиваем фичи. Каждый этап заканчивается рабочим деплоем в dev-бот.

---

## Этап 0. Каркас и инфраструктура
- `package.json`, `tsconfig`, `wrangler.toml` (биндинги D1/KV/R2/AI, маршруты).
- grammY-скелет: webhook, `/start`, эхо для проверки.
- Структура папок: `src/bot` (хэндлеры), `src/ai` (AIProvider), `src/db` (D1/Drizzle), `src/domain` (логика советов/КБЖУ), `src/miniapp` (React-SPA).
- CI-минимум: `tsc --noEmit`, локальный `wrangler dev`.
- **Готово, когда:** dev-бот отвечает на `/start`.

## Этап 1. Данные и онбординг с расчётом целей
- Схема D1 + миграции (users, food_log, state_log, recommendations, weight_log, analytics_events).
- Онбординг: пол/возраст/вес/рост/активность/цель → **TDEE (Mifflin-St Jeor)** → цель КБЖУ.
- Профиль в D1, дисклеймер «не медсовет».
- **Готово, когда:** новый пользователь проходит онбординг, цели сохранены и считаются корректно.

## Этап 2. AIProvider + распознавание фото блюда
- Интерфейс `AIProvider`: `recognizeFood(image)`, `recognizeMenu(image)`, `recognizeLabel(image)`, `advise(ctx)`, `chat(history)`.
- Реализация на Workers AI (vision), строгий JSON через Zod.
- Поток: фото → 200 OK сразу (`waitUntil`/Queue) → распознавание → карточка «Это [блюдо], ~X ккал, порция ~Yг. Верно?» с кнопками **подтвердить / править порцию / править блюдо / ручной ввод**.
- Митигация веса порции: при низкой `confidence` — уточняющий вопрос до записи.
- **Готово, когда:** фото еды превращается в запись дневника после подтверждения.

## Этап 3. Дневник, прогресс, ручной ввод
- Итоги дня (КБЖУ потреблено/осталось до цели), лента приёмов, день и его сброс (по таймзоне).
- Ручной ввод приёма (фоллбэк к фото).
- **Готово, когда:** видно прогресс дня и историю приёмов; можно добавить приём без фото.

## Этап 4. Чек-ин состояния (контекстный)
- Инлайн-чек-ин: набор состояний зависит от времени суток и факта еды (натощак vs после еды).
- Запись в `state_log`, привязка к ленте дня.
- **Готово, когда:** состояние фиксируется в 2-3 тапа и видно в дневнике.

## Этап 5. Движок советов (ИИ + детерминированный fallback)
- **Матрица «время × состояние × макросы»** + Damage-Control сценарии (перенос логики из прототипа `aiService`).
- Совет через Workers AI; при ошибке/слабом ответе — **rule-based fallback** (гарантированный ответ).
- Контракт совета: `{ status, headerStatus, adviceText, recommendedProduct, actionText }`.
- **Готово, когда:** в любой ситуации бот выдаёт корректный совет, даже при отказе ИИ.

## Этап 6. Корзина по дефицитам + диплинк
- Из совета формируется корзина (список продуктов под дефициты дня).
- Кнопка «Заказать» → партнёрский диплинк/ссылка; логируем `basket_click`.
- **Готово, когда:** совет → корзина → клик уходит в партнёра и считается в аналитике.

## Этап 7. Чат с ИИ-нутрициологом
- Свободный диалог (персона), контекст = профиль + дневник дня + состояние.
- История диалога в KV/D1, ограничение длины контекста.
- **Готово, когда:** пользователь может спросить текстом и получить осмысленный ответ с учётом его данных.

## Этап 8. Режимы скана: меню и этикетка
- `recognizeMenu` (фото меню → список блюд с КБЖУ, выбор позиции).
- `recognizeLabel` (этикетка/состав → КБЖУ; задел под штрих-код + Open Food Facts).
- **Готово, когда:** оба режима дают записи в дневник.

## Этап 9. Трекинг веса
- Ввод веса, `weight_log`, текстовая сводка тренда (графики — в Mini App, этап 11).
- **Готово, когда:** вес сохраняется и виден тренд.

## Этап 10. Аналитика и KPI
- `analytics_events` на всех ключевых действиях (photo, confirm, edit, state_checkin, rec_shown, basket_click, chat).
- Простая выгрузка метрик KPI-набора (retention/частота, edit/confirm, CTR корзины).
- **Готово, когда:** метрики собираются и доступны для просмотра.

## Этап 11. Telegram Mini App (тяжёлые экраны)
- Переиспользуем React-прототип: дашборд, история, графики веса/adherence.
- Хостинг на CF Pages/Workers; авторизация через Telegram `initData` (валидация на бэкенде).
- Серверный API (Worker) для данных Mini App.
- **Готово, когда:** из бота открывается Mini App с реальными данными пользователя.

## Этап 12. Проактивные напоминания
- Триггеры: напоминание о чек-ине/приёме пищи (cron Workers / scheduled).
- Настройка частоты, отключение.
- **Готово, когда:** бот шлёт напоминания по расписанию, пользователь управляет ими.
